# prosthesis Orchestrator

Simple MQTT logger that subscribes to topics and stores each message in PostgreSQL.

Each log row contains:
- `id` (from payload `id` when present, otherwise generated UUID)
- `received_at` (UTC timestamp generated by the app)
- `payload` (JSON message content)

## Tech stack
- Python 3.12
- MQTT client: `paho-mqtt`
- Relational database: PostgreSQL 16 (`jsonb` payload)
- Local broker: Eclipse Mosquitto
- Runtime/orchestration: Docker Compose

## Local run

1. Create `.env` from example:

```bash
cp .env.example .env
```

On Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

2. Start all services:

```bash
docker compose up --build
```

3. Publish a test MQTT message:

```bash
docker compose exec mosquitto mosquitto_pub -h localhost -t prosthesis/logs -m '{"id":"msg-001","temperature":36.8}'
```

4. Query logs in PostgreSQL:

```bash
docker compose exec postgres psql -U prosthesis_user -d prosthesis_logger -c "SELECT id, received_at, payload FROM message_logs ORDER BY received_at DESC LIMIT 10;"
```

## AWS run

Use `docker-compose.aws.yml` when you deploy to AWS and want only the Python app + PostgreSQL.
This file keeps MQTT settings from `.env` and removes the local Mosquitto service.

```bash
docker compose -f docker-compose.aws.yml up --build -d
```

The app will read these MQTT values from `.env` as usual:

- `MQTT_HOST`
- `MQTT_PORT`
- `MQTT_USERNAME`
- `MQTT_PASSWORD`
- `MQTT_TLS`

For AWS, the app connects to the external broker defined in `.env`, while PostgreSQL stays inside the same Compose stack.

## Migrations

`db/init.sql` runs only when PostgreSQL data volume is created for the first time.
For schema changes after that, run SQL files from `db/migrations` manually.

Run all pending migrations:

```bash
python -m app.migrate
```

docker compose exec postgres psql -U prosthesis_user -d prosthesis_logger -c "SELECT filename, applied_at FROM schema_migrations ORDER BY applied_at DESC;"

## Configuration
All config is done with environment variables in `.env`.

- `MQTT_HOST`, `MQTT_PORT`, `MQTT_USERNAME`, `MQTT_PASSWORD`
- `MQTT_LOGS_TOPIC` (comma-separated)
- `MQTT_QOS`
- `MQTT_POWER_FEEDBACK_TOPIC`, `MQTT_POWER_FEEDBACK_PARSED_TOPIC`
- `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`
- `LOG_LEVEL`

## Power command feedback

The communication bridge answers every power command (`16` / `17`) with a JSON message on
`MQTT_POWER_FEEDBACK_TOPIC` (default `prosthesis/actions/feedback`). The value must match the
bridge's own `MQTT_POWER_FEEDBACK_TOPIC` on the Raspberry Pi.

For each feedback message the orchestrator:

1. stores it in `logs` with `sensor_name = power_feedback`, level `INFO` on `success` and
   `ERROR` on `failure`, and the bridge `message` kept verbatim in the log text;
2. republishes the normalized payload (`timestamp`, `command`, `status`, `state`, `message`)
   on `MQTT_POWER_FEEDBACK_PARSED_TOPIC` (default `prosthesis/actions/feedback/parsed`).

Malformed feedback (missing field or unknown enum value) is logged and discarded.

```bash
docker compose exec mosquitto mosquitto_pub -h localhost -t prosthesis/actions/feedback \
  -m '{"timestamp":"2026-08-17T12:00:00.421870000+00:00","command":"power_on","status":"success","state":"on","message":"started RoboticLegControl (sudo pid 4312)"}'
```

## Cloud migration (same app image)
For production/cloud, keep this Python app unchanged and switch only endpoints/credentials:

1. Broker options (managed MQTT):
   - HiveMQ Cloud
   - EMQX Cloud
2. Database options (managed PostgreSQL):
   - Neon
   - Supabase
   - Railway

Then set cloud values in environment variables (including auth/TLS settings if needed).

## Notes
- This MVP is designed for readability and easy setup.
- Works on different OS and CPU architectures through Docker images.
- For higher throughput in the future, add batching/queueing before DB insert.
